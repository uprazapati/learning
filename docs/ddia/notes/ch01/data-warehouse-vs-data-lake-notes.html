Data Warehouse vs. Data Lake

Why organizations ended up with two different places to keep analytical data — and what each one is actually good at. From DDIA, Chapter 1 ("From data warehouse to data lake").

data warehouse data lake

01 The one-line difference

Data warehouse — a relational database, queried with SQL, often through BI software. Data is cleaned and shaped into a fixed schema before it goes in.
Data lake — a centralized repository of raw files — any format, no schema required. Data goes in almost exactly as it came out of the source system, via ETL.

Same underlying data, two different philosophies about when you decide its structure: up front (warehouse) or later, whenever someone actually reads it (lake).

02 Why the warehouse wasn't enough

A warehouse is great for a business analyst asking "what were sales by region last quarter?" — a SQL query answers that cleanly. It's a worse fit for a data scientist who needs to:

  • Turn rows and columns into a vector of numbers — features — to train an ML model. This feature engineering step usually needs custom code that's awkward to express as SQL.
  • Run NLP over text (reviews, support tickets) or computer vision over images to pull out structure that wasn't there in the first place.

So most data scientists reach for Python (Pandas, scikit-learn), R, or Spark instead of writing SQL against the warehouse — tools a relational database doesn't naturally serve.

03 The data lake's answer

Give data scientists a copy of everything, in its rawest form, and let each person shape it however their own tool needs:

  • No fixed file format — Avro or Parquet records, plain text, images, video, sensor readings, even genome sequences
  • Filled by the same ETL processes that feed the warehouse
  • Usually cheaper to run — commodity object storage (like S3), not a relational engine
Wait, "ETL" into a raw lake? — If nothing's being transformed, why call it ETL? Because there's usually still a thin, technical transform: re-encoding data from the operational system's internal format into a file format the lake can store, like Avro or Parquet. That's a structural transform, not a business-logic one — no cleaning, no reshaping into a schema. What actually happens is closer to ELT (Extract → Load → Transform later, whenever someone reads it) than classic ETL. The book itself hedges on this a paragraph later, switching to the more general term data pipeline instead of ETL.
The sushi principle — "raw data is better." Keep the unprocessed original around, and let every consumer transform it their own way, instead of committing to one transformation up front.

04 How the data actually flows

ETL has generalized into data pipelines, and the lake is now often just a stop along the way to the warehouse — not a dead end. Business analysts still get their clean, relational warehouse; data scientists get direct access to the raw material instead of waiting for someone to shape it for them first.

07 Reverse ETL — closing the loop

The goal — get an answer that was worked out in the warehouse in front of the person who needs it, without them having to go open a dashboard to find it.

Everything so far moves data into the warehouse/lake. Reverse ETL runs that the other way: it takes something computed in the warehouse and writes it back out into the tools people already work in all day — their CRM (the customer database sales teams use, e.g. Salesforce), a support tool, an email tool.

Example: the warehouse works out which customers are likely to cancel ("churn risk"), once, using SQL, across every customer. Reverse ETL then writes that score onto each customer's record in the CRM — so a sales rep just sees "churn risk: high" sitting there already, instead of going to look it up somewhere else.

08 Turning raw data into "recommended for you"

The goal — take the raw clicks and purchases already sitting in the data lake, and turn them into something a real person sees on screen, like Amazon's "customers who bought this also bought…" row.

Here's the path from raw data to that one feature, step by step:

  • 1. The raw signal is already there. Every click and purchase a user makes already lands in the data lake — that's just the same ETL pipeline from section 03, nothing new.
  • 2. Find the pattern. A program looks across everyone's history and learns things like "people who buy X often also buy Y." This pattern-finding step is what people mean by "training a model" — think of it as building a giant lookup table, except the computer works out the rules from examples, instead of a person writing them by hand.
  • 3. Save that pattern-finder somewhere reliable. This is all TFX, Kubeflow, and MLflow actually do — keep track of which version is the current one, and make it safe to swap in a fresher version later without breaking anything. They're just bookkeeping for step 2 — they don't change the idea, they make it safe to run in a real company with real traffic.
  • 4. Ask it, live. When you open the product, it asks the pattern-finder "given what this person has done, what should we show them?" — the ranked answer becomes the "recommended for you" row.

Same shape as reverse ETL, one section up: something gets worked out centrally, then the answer gets pushed out to wherever a person actually sees it — a CRM there, the product itself here.

09 Where this is heading

As pipelines matured, organizations started paying more attention to managing them — governance, privacy, and compliance (GDPR, CCPA) all push toward treating data pipelines as first-class, operated systems rather than a one-off ETL script. The DataOps movement is the name for that shift.
