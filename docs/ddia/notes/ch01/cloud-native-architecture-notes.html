Cloud-Native System Architecture

"Runs in the cloud" and "cloud native" are not the same thing — and the difference is exactly what gets you better performance, faster recovery, easier scaling, and bigger datasets. From DDIA, Chapter 1 ("Cloud Native System Architecture").

generic (self-hosted-style) cloud native

01 Two ways to use the same cloud

The goal — tell apart "I moved my old system onto a cloud machine" from "I built a system that actually exploits what the cloud can do" — because only the second one gets you the good stuff.

Almost any self-hosted software can just be lifted onto a rented cloud virtual machine (IaaS) and left to run exactly as before — same generic CPU, RAM, and local disk it always used, just rented instead of owned. That's using the cloud, but the software itself hasn't changed.

Cloud native — means the software was designed around the cloud provider's own building blocks from the start, instead of pretending it's still talking to one ordinary computer.

02 The building block that makes it work: object storage

The clearest example is object storage — services like Amazon S3, Azure Blob Storage, or Cloudflare R2. Compared to a normal filesystem it can feel limited (it's mostly just "save this file, read this file back"), but it comes with three things a single machine's disk never could:

  • Your data is automatically spread across many machines, not one
  • If a machine or its disk fails, no data is lost — you never even notice
  • There's effectively no size limit — you're not capped by one disk's capacity

A cloud-native database builds on top of that, instead of managing its own disks the way self-hosted software does. Snowflake, for example, is a cloud data warehouse that actually stores its data in S3 — and other services, in turn, get built on top of Snowflake. It's layers all the way down.

03 Why cloud-native avoids virtual disks

Cloud providers also sell virtual disks — Amazon EBS, Azure managed disks, GCP persistent disks — as an alternative to a VM's own local disk (which disappears the moment that instance is resized or fails). A virtual disk can be detached from one instance and reattached to another. But it isn't actually a disk: it's a separate service, run by its own set of machines, that emulates the behavior of a disk (a "block device," working in fixed 4 KiB chunks) — purely so old, disk-based software can run in the cloud unmodified.

The cost of pretending — that emulation isn't free. It adds overhead a purpose-built system wouldn't need, and because the "disk" is really somewhere else on the network, every single read/write becomes a network call — the whole system becomes sensitive to ordinary network hiccups in a way a real local disk never would be.

Cloud-native systems sidestep this by building on dedicated storage services like S3 instead. S3 isn't pretending to be a disk — it exposes its own simple "save this file, read it back" API, purpose-built for storing large files long-term. No emulation, so none of the emulation's cost.

 Virtual disk (EBS, Azure managed disk)Dedicated storage (S3)

Same underlying lesson as section 02: a cloud-native system gets its advantages by using a service designed for the job, rather than one that's just imitating an older piece of hardware.

04 Why that layering pays off

Each advantage traces back to one thing: a cloud-native system inherits properties the lower-level cloud service already solved, instead of solving them itself, badly, from scratch.

AdvantageWhy building on the cloud's own services gets you this
Better performance, same hardware You're riding on infrastructure the provider already spent years optimizing at huge scale — not reinventing it yourself, less efficiently.
Faster recovery from failures The underlying storage already assumes machines fail constantly and handles that automatically. A traditional single-server system has to notice the failure and recover manually.
Scales quickly to match load Storage and compute are separated — you can add or remove compute machines in minutes without physically moving any data.
Supports much larger datasets Object storage has no real capacity ceiling, so you're not limited by how big a disk you can attach to one machine.

06 No universal right answer, again

Higher-level, cloud-native services tend to be built for particular use cases. If your needs match what one was designed for, using it will almost always be less hassle than building the equivalent yourself on lower-level pieces. If your needs don't match, you're back to the same build-vs-buy, control-vs-convenience trade-off from the last note — just one layer further up the stack.
