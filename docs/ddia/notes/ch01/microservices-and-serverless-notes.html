Microservices and Serverless

Splitting one big application into many small, independently-owned services — and a newer way of deploying each of those services without thinking about servers at all. From DDIA, Chapter 1 ("Microservices and Serverless").

services / microservices serverless

01 Same old idea, sharper name

The most common way to spread a system across multiple machines: split it into clients and servers, and let clients make requests to servers (usually over HTTP). Nothing new there — the same process can even be both at once, serving requests from some callers while making its own requests to other services.

Why he bothers to say this — cloud-native systems lean on splitting into services very heavily (the cloud provider's own services, like S3, are services with one well-defined purpose), which makes it tempting to assume "services" is a cloud idea. It isn't. This way of building applications has had a name for decades: service-oriented architecture (SOA) — and on-premises systems have been built this way since long before "cloud native" was a phrase. More recently, that same idea got refined and renamed microservices architecture.

02 SOA vs. microservices — refined, not replaced

The book treats these as the same idea at two points in time, not two different things — microservices is SOA, sharpened. What specifically sharpened on the way from one name to the other:

  • One well-defined purpose per service — e.g. S3's whole job is file storage, nothing else.
  • Each service exposes an API that other services call over the network.
  • One team owns each service, end to end.

(Beyond what the book spells out here: older SOA setups often ran through heavier middleware — an "enterprise service bus" routing everything centrally — and services were often bigger and more bundled. Microservices push toward smaller, more independent pieces. That's general industry convention layered on top, not a distinction the book draws explicitly in this section.)

03 Why bother splitting it up at all

BenefitWhy it helps
Independent updates One team ships a change to their service without having to coordinate with every other team.
Right-sized hardware Each service gets exactly the resources it needs, not whatever the whole monolith was sized for.
Hidden implementation Clients only ever see the API. The team behind it can rewrite the internals freely, as long as the API doesn't change.

04 Why services (usually) don't share a database

The rule — each service gets its own database. Databases don't get shared between services.

Two concrete reasons, both tracing back to the "hidden implementation" benefit above:

  • Sharing breaks the hiding. If two services read/write the same database, that database's schema has effectively become part of the API between them — except nobody designed it that way, and now it's hard to change without breaking the other service.
  • Noisy neighbors. A heavy, slow query from one service can drag down performance for a completely unrelated service, purely because they happen to share the same database underneath.

05 Serverless: outsourcing "when does this run"

Serverless / FaaS (Function as a Service) — a way of deploying a service where the cloud provider handles starting up and shutting down the hardware for you, automatically, based on incoming requests. With a VM, you decide when it starts and stops; with serverless, the provider does that for you, per request.

The book draws a direct parallel to something we've already covered: object storage replaced manual capacity planning (deciding in advance how many disks to buy) with metered billing (pay for what you actually store). Serverless does the same thing for code execution — you pay only for the time your code is actually running, instead of paying to keep a server provisioned and idle between requests.
