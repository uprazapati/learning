Real-time OLAP vs. traditional OLAP

What Apache Pinot and Druid actually do differently from Snowflake, BigQuery and Redshift — worked through with the LinkedIn feed and Uber surge pricing as running examples.

real-time OLAP — Pinot, Druid, ClickHouse traditional OLAP — Snowflake, BigQuery, Redshift
01

Two different jobs, both called "OLAP"

The split isn't about which one is "better" — it's about what each was built to serve.

Traditional OLAP (data warehouses like Snowflake, BigQuery, Redshift, or legacy cubes) is built for internal business reporting over batch data: a handful of analysts running heavy, flexible SQL. Real-time OLAP (Pinot, Druid, ClickHouse) is built to power live, interactive applications for thousands of concurrent users — the engine sitting behind a product feature, not behind a dashboard a person refreshes once an hour.

The difference comes down to three axes: ingestion speed, query latency, and concurrency.

terms in table 1
  • Filtered aggregation: keep only matching rows, then summarize them (count, sum, average) on one table. E.g. views of post 123 per country in the last hour.
  • Columnar storage: each column's values are stored together, so a query reads only the columns it needs. It still checks every value in those columns to find matches.
  • Custom columnar indexes: the engine's own lookups on top of the columns. An inverted index lists the rows for each value (IN: rows 1, 3), so there's no scan. A star-tree index keeps totals already added up.
  • Local NVMe SSD: NVMe = Non-Volatile Memory Express, a very fast way to connect an SSD. Local = inside the server running the query. A read takes about 0.1 ms, while one S3 request takes tens of ms.
02

The three structural trade-offs

Everything downstream follows from these.

Fresher data vs. deeper queries. Pinot and Druid consume streaming events one at a time — an event posted to Kafka is queryable within milliseconds. A warehouse processes in micro-batches or ETL jobs, so freshness is usually minutes to hours behind.

Concurrency scaling and cost. A dashboard refreshed by 50,000 external users at once on Snowflake or BigQuery would be cost-prohibitive — serverless compute has to scale with every query. Pinot and Druid instead lean on aggressive pre-aggregation and specialized indexing, so high-QPS workloads stay cheap.

Schema rigidness. Real-time engines need the data denormalized (flattened: related tables merged into one wide table ahead of time, so queries need no joins) before it's ingested to hit that speed. Warehouses allow ad-hoc joins across dozens of normalized tables with no pre-flattening required.

mental shortcut Traditional OLAP optimizes for how much you can ask in one query. Real-time OLAP optimizes for how many people can ask at once.
03

Where it's actually used: feeds and surge pricing

LinkedIn built Pinot in 2014 specifically for this problem; Uber later adopted it as a core engine.

LinkedIn feed & member metrics. Serving personalized metrics — feed counts, "who viewed your profile," post analytics — to 1B+ members adds up to 250,000+ requests per second. That isn't 1B divided by anything: it's active members × pages they open × Pinot queries per page. A warehouse would fall over or become unaffordable at that concurrency. Like/view/comment events stream from Kafka into Pinot, get turned into inverted and star-tree indexes in memory, and get read back in under 50ms.

Uber surge pricing & dispatch. Surge pricing needs supply-vs-demand counted inside geofenced hexagons every few seconds — a one-minute delay means lost rides or lost revenue. Every location ping streams through Kafka into Pinot, which also supports real-time upserts (tracking a driver's latest position rather than appending endless history). Pricing algorithms query Pinot hundreds of times per second and get answers in under 100ms.

04

One scroll, two different queries

Scrolling a feed isn't one call to Pinot — it's a write and, separately, a read.

Scrolling past a post writes to Pinot: the app records that a post was visible for 300ms+, sends that impression event to Kafka, and Pinot ingests it within milliseconds, updating its indexes. Requesting the next batch of posts reads from Pinot: the feed recommendation engine asks Pinot how fast a post is accumulating likes and impressions right now, and uses that signal to rank what you see next.

fig. 2 — the same Pinot cluster serves both directions of the loop

Opening your own creator analytics dashboard is the most direct case — the backend fires a query straight at Pinot:

SELECT count(*), company_industry, job_title FROM post_impressions WHERE post_id = '123456' GROUP BY company_industry, job_title;

Pinot processes that across millions of rows and returns the breakdown in under 50ms.

05

Throughput ≠ concurrency

This was the confusing part — both "types" of OLAP get called high-throughput, but they mean different things by it.

Traditional OLAP is high data throughput — scanning gigabytes per second for a single heavy query — but low query throughput (tens to hundreds of concurrent queries). Real-time OLAP is high query throughput — tens of thousands of concurrent queries per second — achieved precisely by doing very little work per query.

The mechanism: instead of scanning raw files, Pinot's broker routes each incoming query only to the specific servers holding the relevant indexed segments — a scatter-gather pattern — and those servers answer from pre-computed indexes in RAM/NVMe rather than scanning columns fresh each time.

06

Why this can't replace Postgres

Speed at analytics doesn't transfer to speed at transactions — they're opposite access patterns.

  1. Storage layout. Postgres keeps a whole row together on disk, so fetching or updating one user is a single fast operation (~0.5ms). Pinot keeps every column in its own file, so reconstructing one full row means opening dozens of files — a point lookup becomes slow and wasteful.
  2. ACID transactions. Postgres has MVCC and row-level locking, so a $50 transfer between two accounts is atomic and race-free. Pinot has no concept of multi-row locks or rollbacks — it can't safely hold a ledger or handle sign-ups.
  3. Mutations. Postgres handles thousands of individual updates/deletes per second effortlessly. Pinot's segments are compressed and immutable — changing a cell means an expensive upsert or a full segment rewrite, and high-frequency random updates make memory usage spike.
  4. Joins & normalization. Postgres joins dynamically across 20+ normalized tables. Pinot needs data flattened before ingestion — heavy dynamic joins defeat its star-tree indexing and kill the latency guarantee.

07

If columns are split into files, how is a 4-column query still fast?

The point-lookup weakness and the aggregation strength come from the same design choice.

A feed analytics query like SELECT sum(impressions), sum(clicks) FROM post_analytics WHERE author_id = X AND date >= Y only touches 4 of a table's 50+ columns. Postgres would still read every column of every matching row off disk. Pinot opens only those 4 column files and ignores the rest — a 90%+ cut in I/O before anything else happens.

Three mechanisms take it from "faster" to milliseconds:

  • Inverted indexes — author_id 987654 → [row 12, row 408, ...] gives the matching row IDs directly from memory, no scanning.
  • Vectorized reads — the matching rows' impressions/clicks columns load into CPU vector registers (SIMD), summing thousands of values per clock cycle.
  • Star-tree pre-aggregation — for popular combinations of dimensions, the sum is already computed at ingestion time and sits in a tree node in RAM, so the query is a lookup, not a calculation.

08

How much data actually gets scanned

Both can store petabytes — the difference is how much of that gets touched per query.

Per query, traditional OLAP can legitimately scan gigabytes to petabytes of raw, un-indexed data to run a deep ad-hoc join. Pinot typically scans only megabytes to a few gigabytes per query, because indexing (inverted indexes, star-trees, bloom filters) lets it skip 95%+ of the dataset before touching disk or memory at all.

Total capacity is a separate question — both scale to petabytes. Traditional warehouses do it cheaply on object storage (S3/GCS) with decoupled compute. Pinot does it across distributed clusters on local SSD/NVMe/memory — Stripe runs 3+ PB in Pinot, Uber and LinkedIn run clusters spanning petabytes of streaming and historical data.

Recap — the two identities

If nothing else sticks, this split should.

Real-time OLAP

  • Streams in from Kafka, queryable in milliseconds
  • Wins on concurrency — thousands of QPS per cluster
  • Answers come from indexes and pre-aggregation, not fresh scans
  • Needs data flattened up front; heavy joins hurt it
  • Sits behind product features, not analyst dashboards

Traditional OLAP

  • Loads in batches, freshness measured in minutes to hours
  • Wins on query depth — full flexible ANSI SQL, any join
  • Answers come from scanning raw columnar files at query time
  • Normalized schemas are fine; no pre-flattening needed
  • Sits behind BI tools and internal reporting
