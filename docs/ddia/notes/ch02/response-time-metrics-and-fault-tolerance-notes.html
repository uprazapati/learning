01 One slow call makes the whole request slow

High percentiles matter most in backend services — especially ones that are called multiple times while serving a single end-user request. Even if you make the calls in parallel, the end-user request still has to wait for the slowest of them to complete. It takes just one slow call to make the entire end-user request slow.

Redrawn from Figure 2-6. The web application calls seven backends in parallel, and the end-user request finishes only when the slowest one (Backend 6, 487 ms) comes back. Six of the seven calls took under 150 ms, but the user still waits 487 ms. Hover a bar for its time.

Even if only a small percentage of backend calls are slow, the more backend calls an end-user request needs, the more likely it is to hit at least one slow one. So a higher proportion of end-user requests end up slow than backend calls.

Tail latency amplification — that effect: slow backend calls are rare, but because one request depends on many of them, slow end-user requests are much less rare.

Beyond the book (my arithmetic). Suppose each backend call is slow (slower than that backend's p99) 1% of the time, independently. A request that makes n calls avoids every slow one with probability 0.99n, so it's slow with probability 1 - 0.99n. Seven calls, as in Figure 2-6, already make 6.8% of end-user requests slow, and 100 calls make 63% slow. Hover a dot for the exact number.

02 SLOs and SLAs

Percentiles are often used in service level objectives (SLOs) and service level agreements (SLAs) as a way of defining the expected performance and availability of a service.

SLO — a target the service should meet. For example: a median response time under 200 ms, a 99th percentile under 1 second, and at least 99.9% of valid requests resulting in non-error responses.
SLA — a contract that specifies what happens if the SLO is not met (e.g. customers may be entitled to a refund).
The book's example SLOWhat gets measuredTarget
Typical speedMedian response time (p50)under 200 ms
Speed of the tail99th-percentile response time (p99)under 1 second
AvailabilityShare of valid requests that get a non-error responseat least 99.9%
"That's the basic idea, at least" — in practice, defining good availability metrics for SLOs and SLAs is not straightforward.
Error budget (beyond the book) — SRE practice calls the 0.1% of requests that are allowed to fail the error budget. My arithmetic: at 1,000 requests per second that's 86.4 million requests a day, so a 99.9% target still allows about 86,400 errors a day.

03 Computing percentiles (the book's sidebar)

To put response-time percentiles on a monitoring dashboard, you need to calculate them efficiently on an ongoing basis. For example, keep a rolling window of the response times of requests in the last 10 minutes. Every minute, calculate the median and various percentiles over the values in that window and plot them on a graph.

My sketch of the rolling window (beyond the book). At 12:00 the percentiles are computed over the requests from 11:50 to 12:00 (blue), and the older ones have aged out (gray). A minute later the window slides forward by a minute and the calculation runs again, adding one new point per percentile to the graph.

Never average percentiles — averaging percentiles (e.g. to reduce the time resolution, or to combine data from several machines) is mathematically meaningless. The right way to aggregate response-time data is to add the histograms.

What goes wrong when you average (my arithmetic) — averaging the two p99s, using the bucket tops, gives (200 + 2,000) / 2 = 1,100 ms. But B served only 100 of the 10,100 requests, so averaging gives it as much say as A. Adding the histograms bucket by bucket keeps every request's weight: the 9,999th fastest of the 10,100 requests falls in the 200–500 ms bucket, which is the real p99. The average overstates it by more than 2x, and with other numbers it can just as easily understate it.
Beyond the book — all four libraries above produce summaries that can be merged, so you can combine the summaries from many machines or time windows into one. That's the "add the histograms" rule built into the data structure.

04 What "reliable" means

Everybody has an intuitive idea of what it means for something to be reliable or unreliable. For software, typical expectations include:

  • The application performs the function that the user expected.
  • It can tolerate the user making mistakes or using the software in unexpected ways.
  • Its performance is good enough for the required use case, under the expected load and data volume.
  • The system prevents any unauthorized access and abuse.
Reliability — if all of those together mean "working correctly," then reliability means, roughly, "continuing to work correctly, even when things go wrong." To be more precise about things going wrong, the book distinguishes between faults and failures.

05 Faults vs failures

Fault — a particular part of a system stops working correctly. For example, a single hard drive malfunctions, a single machine crashes, or an external service the system depends on has an outage.
Failure — the system as a whole stops providing the required service to the user. In other words, it does not meet the SLO.
Same thing, different levels — the distinction is confusing because faults and failures are the same thing at different levels. If a hard drive stops working, the hard drive has failed. If the system consists of only that one drive, it has stopped providing the required service, so the system has failed too. But if the system has multiple drives, one drive failing is only a fault from the bigger system's point of view, and the system might tolerate it by having a copy of the data on another drive.

My drawing of the book's hard drive example. The same broken drive is a failure on the left and only a fault on the right, because the system on the right has a copy of the data on another drive.

(This ties back to section 02. Because a failure means missing the SLO, and the SLO includes response-time percentiles, a system that is up but too slow to meet its SLO has failed as well. That follows from the book's definition, though the book doesn't say it in so many words here.)

06 Fault tolerance and single points of failure

Fault-tolerant — a system that continues providing the required service to users in spite of certain faults occurring.
Single point of failure (SPOF) — a part of the system that it cannot tolerate becoming faulty, because a fault in that part escalates to cause the failure of the whole system.

The book's example, from the social network case study: during the fan-out process, a machine that's updating the materialized timelines crashes or becomes unavailable. To make fan-out fault-tolerant, another machine has to take over the task without missing any posts that should have been delivered, and without duplicating any posts.

Exactly-once semantics — the name for that "nothing missing, nothing duplicated" guarantee. The book examines it in detail in Chapter 12.

My illustration (beyond the book). One new post has to land in six followers' timelines. Machine A crashes after F3. If B starts over, F1–F3 get the post twice. If B misjudges where A stopped, F4 never gets it. Only resuming at exactly the right place gives exactly-once.

Fault tolerance is always limited — to a certain number of certain types of faults. For example, a system might tolerate at most two hard drives failing at the same time, or at most one out of three nodes crashing. Tolerating any number of faults makes no sense: if all nodes crash, nothing can be done. If the entire planet Earth (and all servers on it) were swallowed by a black hole, tolerating that fault would require web hosting in space. "Good luck getting that budget item approved."

07 Causing faults on purpose

Fault injection — counterintuitively, in fault-tolerant systems it can make sense to increase the rate of faults by triggering them deliberately, for example by randomly killing individual processes without warning.

Why it helps: many critical bugs are actually due to poor error handling. By deliberately inducing faults, you make sure the fault-tolerance machinery is continually exercised and tested. That increases your confidence that faults will be handled correctly when they occur naturally.

Chaos engineering — a discipline that aims to improve confidence in fault-tolerance mechanisms through experiments such as deliberately injecting faults.
Beyond the book — the best-known example is Netflix's Chaos Monkey, which randomly terminates production instances so that teams have to build services that survive it.

Beyond the book — the bad CPU cores are what Google's 2021 paper "Cores that don't count" calls mercurial cores. A crash is a fault you notice; a silently wrong answer isn't. The bit-flipping access patterns in the RAM row are the effect known as Rowhammer.
Why SSDs have the higher error rate but die less often — it's two different measures. An SSD is less likely to die outright (0.5%–1% a year vs 2%–5%), but more likely to lose a block of data (about one uncorrectable error per drive per year). Beyond the book: flash stores bits as tiny charges that leak and get disturbed by nearby reads and writes, so the drive's error-correcting code is fixing a few wrong bits all the time, and past its limit that data is lost. Hard drives store data magnetically, which is more stable, but they fail mechanically, so the whole drive dies.
